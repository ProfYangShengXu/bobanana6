# bobanana6 · 架构设计

> 一句话：**用充裕的并发资源，把复杂任务切成 N 块分工砸完；三层约束保证每块合格、语义一致、整体拼得上。**

---

## 0. 先说人话

```
串行路线    一个模型，有限预算，一步一步做
            瓶颈 = 单次能力。手段是"让这一次更容易成功"

并行路线    一群 agent，各做一块，拼起来
            瓶颈 = 可切分性 × 局部重试 × 装配一致性 × 【语义一致】
            天花板由并发槽决定，也由任务形状决定
```

**bobanana6 走第二条。核心命题：**

> **砸死任务的前提不是模型强，是任务能被切成「接口明确 + 可独立验证 + 可局部重试 + 语义有共同定义」的块。**

切得出来，并发槽就是杠杆；切不出来，加几倍资源都是自残。

---

## 1. 三层约束，与「共享语义」的真实来源

```
┌────────────────────────────────────────────────────────────┐
│  L-1 · 共享语义 SharedSemantics                             │
│     概念表 / 术语表 / 单位量纲 / 口径定义 / 关系 / 编码表      │
│     ★ 关键性质不是「外部给定」，而是【前置 + 唯一 + 冻结】     │
│        · 前置：worker 开工前就定好                             │
│        · 唯一：全局一份，不是每个 agent 各形成一份              │
│        · 冻结：切分开始后不再变                                │
└───────────────────────────┬────────────────────────────────┘
                            │ 约束包只能【引用】，不能各自另立
┌───────────────────────────▼────────────────────────────────┐
│  L0 · 任务契约 TaskContract      每个任务一份               │
│     目标 / 交付物清单 / 验收口径 / 可用源                    │
└───────────────────────────┬────────────────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────────┐
│  L1 · 切分方案 + 约束包           每任务编译一次（可迭代）    │
│     ★ 每个字段/指标必须映射到 L-1 的概念                      │
└────────────────────────────────────────────────────────────┘
```

### 1.1 为什么必须有共享语义

**单 agent 没有这个问题。** 它用自己的隐含理解保持全文自洽——同一个词在它脑子里始终指同一个东西。

**多 agent 没有共享的隐含理解。** 每个 agent 独立形成自己的理解，于是：

```
agent A 产出的 customer_id = 账户号
agent B 产出的 customer_id = 客户主体号
两边都叫 customer_id，都是 int → schema 检查通过 → 装配后数据全错
```

**这就是 Cognition 说的 "actions carry implicit decisions"** —— 并行 agent 各自带着隐含选择，必然冲突。

**解药只有一个：把隐含的东西显式化，且全局只有一份。**

> ★ **注意分清两件事**：解决这个问题需要的是**一致性**，不是**权威性**。
> 「外部给定」是权威性需求，那是企业才有的条件（治理团队、标准体系、签版的人）。
> 混为一谈会把产品做成只对企业可用。

**代价是真实的**：多 agent 要额外维护一份共享语义。这是它相对单 agent 的**结构性成本**，优化不掉。

### 1.2 面向个人开发者：语义从哪来

个人开发者**没有治理团队、没有标准体系、没有领域专家签版**。如果共享语义是必填的外部输入，产品对目标用户直接不可用。

**所以 `OntologyPort` 提供四条来源，默认走第一条：**

| | 来源 | 谁用 | 成本 | 说明 |
|---|---|---|---|---|
| **①** | **自动起草（默认）** | 个人开发者 | 一次模型调用 | 从任务契约 + 输入数据 schema 推出概念表 |
| ② | 复用上次 | 重复同类任务 | 0 | 同一 project 下增量扩充 |
| ③ | 导入标准 | 企业 / 领域有标准 | 映射器人力 | SKOS / OWL / FIBO 等 |
| ④ | 手工编写 | 有明确口径要求 | 人力 | 直接写 YAML |

**四条路产出同一个 `Ontology` 对象、走同一套校验、对 `core/` 完全不可区分。**
换来源 = 换 `OntologyPort` 实现，`core/` 一行不动。

### 1.3 自动起草会不会退化回「自说自话」

**不会——只要满足前置、唯一、冻结三条。**

失败模式从来不是「语义由模型生成」，而是**「每个 agent 各自形成理解」**。一份起草出来的、全局共用的、开工前冻结的语义层，和一份标准委员会发布的，对多 agent 的一致性作用**是一样的**。

**但起草会错，而个人开发者没有权威可对照。** 三层兜底：

```
① 零模型自洽性检查（core/ontology.py 能做）
   概念无循环定义 / 单位换算自洽 / 口径不互相矛盾 / 别名不冲突
   ★ 它判不了「定义对不对」，但能判「你自己的定义互相打不打架」

② 分歧机制自动暴露
   两个 agent 对同一概念产出不同结果 → 走 BlindSpot / Conflict 通道
   ★ 语义层的问题会以「分歧」的形式自己浮出来，不需要专门的检测器

③ 落盘可审
   起草结果写成 YAML，人扫一眼的成本远低于「从零写一份本体」
```

**②是这套设计的一个意外红利**：语义层质量问题复用了已有的分歧机制，不用新增一套检测。

### 1.4 个人版和企业版的差别只在「语义层多厚」

```
企业版   预置大本体（整个领域），跨项目复用
个人版   按需生成【最小本体】—— 只含这次任务用到的概念
         任务变了再增量扩充，不做前置投资
```

**语义层的投资回报窗口对个人很短**（任务可能只跑一次），所以**默认不预置、按需生长**。
落盘在 project 目录下，同类任务第二次运行直接复用。

### 1.5 语义层装什么

```yaml
# .bobanana6/ontology.yaml —— 默认自动起草后落盘；企业可换成导入既有标准
domain: credit-risk
version: "2026.1"

concepts:
  credit.rating:      {label: 信用评级, kind: attribute, code_system: rating_scale}
  credit.pd:          {label: 违约概率, kind: measure, unit: ratio}
  credit.lgd:         {label: 违约损失率, kind: measure, unit: ratio}
  obligor.id:         {label: 债务人主体号, kind: entity}
  account.id:         {label: 账户号, kind: entity}

relations:
  - {src: account.id, dst: obligor.id, kind: belongs_to, cardinality: "N:1"}
  - {src: credit.pd, dst: obligor.id, kind: measured_on}

definitions:
  credit.pd:
    version: "2026.1"
    text: 未来 12 个月内发生违约的概率，按债务人主体计，不按账户计
    edge_cases: [重组后重新起算, 逾期 90 天即视同违约]

units:
  credit.pd: {symbol: ratio, scale: 1.0, base: ratio}

code_systems:
  rating_scale: [AAA, AA+, AA, AA-, A+, A, A-, BBB+, BBB, BB, B, CCC, CC, C, D]

calendar: {timezone: Asia/Shanghai, trading_days: SSE}
```

**注意 `definitions` 里的口径**：`按债务人主体计，不按账户计` —— 这一句就能挡掉上面那个 `customer_id` 的坑。

### 1.6 语义层把「冲突」分成两种

**这是它最大的实际价值。** 两个来源给出不同的值，先查口径：

```
两个来源对同一字段给出不同值
      │
      ├── 引用的 Definition 版本不同  → 【口径不一致】→ 这是【缺陷】，不是冲突
      │                                  归一后重比（不记录为冲突）
      │
      └── 同口径但值不同              → 【真冲突】→ 记录，保留双方证据
```

**不做这一步的后果**：把口径差异当成数据冲突，报告里会充满假冲突；把数据冲突当口径问题去"归一"，会把真实矛盾抹平。**两个方向都是错的。**

**所以 `DefinitionMismatch` 是缺陷类（要修），`Conflict` 是信号类（要留）** —— 混在一起就无法正确处理。

## 2. 两类任务，两套切法

| | 代码类 | 信息收集与处理类 |
|---|---|---|
| **接口从哪来** | 语言已给好（模块/函数/类） | 要推断出来（schema/实体/字段） |
| **切分维度** | 层次切分 | 按**源**／**实体**／**时间窗**／**字段** |
| **验证手段** | 跑测试（确定性） | **溯源** + **交叉验证** |
| **可复现** | 同输入必同输出 | 输入是活的，**必须快照** |
| **成本瓶颈** | 模型 token | **取网**（速率/反爬/代理） |
| **对本体论依赖** | 中（类型系统已给一半） | **高**（口径全靠它） |
| **读写比** | 常偏高（要改文件） | 常偏纯读 |

**为什么代码能砸死**：不是代码简单，是**切分不需要发明**——语言把接口替你做好了。

### 2.1 读写比是并行度的硬上限

**Cognition 用血换的教训**：一个 agent 做的改动里带着隐含选择（风格、边界处理、命名），
和另一个 agent 的选择**必然冲突**。所以**绝大多数多 agent 系统的 subagent 是只读的**。

```
可并行比例 ≈ 任务里【读】的部分 / 全部
```

**写操作要么串行，要么分区隔离**（OpenHands 的做法：git worktree，一 agent 一份）。

**这条直接限定了"砸死"的适用面**：读密集型（调研、抽取、验证、测试生成）能砸；
写密集型（一堆 agent 一起改同一份代码）砸不动——不是架构不行，是任务形状不行。

### 2.2 混合任务是网格

```
           抓取      抽取      清洗      验证      综合
来源 A  ──  ●  ──→   ●  ──→   ●  ──→   ●  ──→
来源 B  ──  ●  ──→   ●  ──→   ●  ──→   ●  ──→    ──→  装配
来源 C  ──  ●  ──→   ●  ──→   ●  ──→   ●  ──→
          └─ fan-out ─┘        每级可并行       └─ fan-in ─┘
```

切分器要能识别"这一级该横切、那一级该竖切"。

## 3. 架构推导：从「什么最容易变」出发

不套模板。层名和数量随场景变，**不变的只有依赖方向**。

### 3.1 列变化频率

| 东西 | 周期 | 依据 |
|---|---|---|
| 具体站点结构、反爬策略 | **周** | 外部环境，最易变 |
| 具体模型 / provider | 季度 | 技术选型 |
| 取网手段 | 季度 | 技术选型 |
| 切分策略 | 半年 | 领域经验 |
| 契约格式 | 半年 | 格式演进慢 |
| 各约束 kind 判定实现 | 半年 | 领域规则演进慢 |
| 约束的数据模型 | 年 | 概念稳定 |
| **判定语义 / 分歧语义 / 切分合法性** | 年 | 领域核心 |
| **★ 本体论内容** | **年+** | **行业标准，十年不变** |

### 3.2 按变化频率切层

```
稳定 ←──────────────────────────────────────────────────────────► 易变

  core/         ontology/     decompose/   contract/  adapters/  sources/
  判定与分歧     本体加载       切分策略      契约解析    模型对接    取网对接
  切分合法性     与映射
  本体校验
  (年)          (年)         (半年)       (半年)     (季度)     (周/季度)
```

**验证方法**：换模型→只改 `adapters/`；换站点→只改 `sources/`；
换判定规则→只改 `core/checkers/`；换领域本体→只改 `ontology/` 的数据文件。

### 3.3 依赖箭头全部指向稳定侧

```
                          ┌──────────────────────┐
                          │        core/         │  ← 一切依赖的终点
                          │  判定 / 分歧 / 溯源    │
                          │  切分合法 / 装配检查   │
                          │  本体校验             │
                          │  ports ★             │
                          └──────────▲───────────┘
                                     │ 实现
   ┌──────────┬──────────┬───────────┼───────────┬──────────┬──────────┐
┌──┴───────┐┌─┴────────┐┌┴─────────┐┌┴─────────┐┌┴────────┐┌┴────────┐
│ontology/ ││decompose/││contract/ ││adapters/ ││sources/ ││ cli.py  │
│本体加载   ││ 切分策略  ││ 契约解析  ││ 模型对接  ││ 取网对接  ││唯一装配点│
└──────────┘└──────────┘└──────────┘└──────────┘└─────────┘└─────────┘
```

**没有一条箭头从 core 指出去。** core 不含 `prompt`/`token`/`http`/`url`/`html` 任何一词。

**强档自检**：把 `ports.py` 拿给一个不懂 LLM、不懂爬虫、也不懂金融的人看，他能看懂吗？

### 3.4 唯一装配点

**`cli.py::build_app()` —— 全项目唯一 new 具体实现的地方。**

### 3.5 运行时数据流（与依赖方向是两回事）

```
L-1 本体论        外部给定，跨任务复用
      ↓
L0  任务契约      目标 + 交付物 + 验收口径 + 可用源
      ↓
L1  切分 + 约束    强模型，迭代：先切粗，跑一轮，再往下切（有轮数上限）
      ↓
L2  判定内核       合格？语义一致？装配拼得上？分歧属哪类？   ← core，零模型
      ↓
L3  worker 集群    按维度 fan-out；读并行、写隔离
      ↓
L4  仲裁           分【约束盲区】【真冲突】【口径不一致】三条路
      ↓
L5  装配 + 溯源    全局不变量 + 每个数据点指回快照
```

**★ 数据流方向 ≠ 依赖方向。** 运行时 L4 在下游，代码上它依赖 core 定义的端口。

## 4. 迭代切分

### 4.1 轮次（有上限）

```
R0 侦察     探明：源可达性 / 实体清单 / 字段填充率 / schema 草案
            ★ 只取样 —— 目的是【知道地形】，不是拿数据
R1 粗切     信息类按【源】，代码类按【模块】
R2 判定     装配检查 → 哪些块缺、哪些字段空洞最多、哪些源死了
R3 细分     只对【空洞大的部分】再切
R4 交叉验证 同口径比对 → 一致？真冲突？口径不一致？
R5 装配     全局不变量 + 溯源完整度
```

**★ 轮数硬上限 3 轮（R1/R3 各算一轮，允许一次回退）。**

理由：切分阶段的 orchestrator 是**串行**的，不能并行，它是整条关键路径。
参照 Kimi K3 Agent Swarm 的做法——他们给 orchestrator 限死 **15 步**，
而 subagent 跑 4000+ 步。**没有上限 = 切分成本无界。**

### 4.2 为什么必须有局部重试（杀手级前提）

**N 块，每块独立失败率 f，无局部重试时全部成功的概率：**

```
N       f=1%     f=5%    f=10%   f=20%
8       92.3%    66.3%    43.0%   16.8%
32      72.5%    19.4%     3.4%    0.1%
100     36.6%     0.6%     0.0%    0.0%     ← 
200     13.4%     0.0%     0.0%    0.0%
```

**加上局部重试（每块最多 r 次）：**

```
N        r=1      r=2      r=3      r=5
8        66.3%    98.0%    99.9%   100.0%
100       0.6%    77.9%    98.8%   100.0%     ← 
200       0.0%    60.6%    97.5%   100.0%
```

**局部重试不是优化项，是 N 能开大的前提条件。**

### 4.3 切分必须是星形

```
N 块两两依赖   →  接口数 N(N-1)/2  →  N=100 时 4950 个接口   ✗ 灾难
N 块对契约     →  接口数 N         →  N=100 时 100 个接口     ✓ 可扩展
```

**这与业界一致**：Cognition 把可行形状总结为 **map-reduce-and-manage**，
并明确说"非结构化 swarm——agent 之间互相协商的自由网络——基本是个干扰项"。

**信息类天然占优**：按源切时源之间本就不依赖。**代码类要小心**：模块间常有真实依赖。

### 4.4 上并行前要过三问

Moonshot 在 Kimi K3 Swarm 文档里给的三条判据，**三条全中才该 fan-out**：

```
① 子任务互相独立        ←→ split.py: star / iface_complete
② 合并成本低            ←→ assemble.py: merge_cost
③ 能容忍分歧            ←→ 分歧分类（Disagreement / Conflict）
```

**只中两条就该重新想，不要 fan-out。**

## 5. 设计决定

### 5.1 切分与判定离线/一次性，不每轮问强模型

强模型在 R1 产出切分 + 约束包，之后集群只用这一份。R3 的细分产出增量，不逐块问。

**反面对照**：每块提交后都让强模型看一眼 → 成本随块数线性增长，且判据可能不一致 → 不可复现。

### 5.2 判定内核零模型

`core/` 是纯代码，`admit()` 是确定性函数。这是"可审计"的前提——由模型判断的内核，
你无法回答"为什么这块拒了那块没拒"。

### 5.3 分歧分三类，走三条路

```
通过 hard 的产物之间有差异
      │
      ├── 先查口径：引用的 Definition 版本一致吗？
      │     不一致 → 【口径不一致】= 缺陷 → 归一后重比，不记为冲突
      │
      ├── 同口径、值不同、且是【不同来源对同一事实】 → 【真冲突】
      │     → 记录，两级证据都留，不取平均、不取多数
      │
      └── 差异落在【约束沉默的字段】上 → 【约束盲区】→ 补约束 → 重跑
```

**三类必须分开。** 合并的话，调用方就无法区分"该修缺陷""该记录信号""该补约束"——
**类型系统是唯一能强制住这条的地方。**

### 5.4 多样性来源：切分维度 > 分解策略 > 温度

```
切分维度   按源/实体/时间窗      → 结构性差异，最有效
分解策略   自顶向下/最小样例/数据先行 → 路径差异
温度       同 prompt 不同采样     → 噪声，基本没用
```

### 5.5 快照先于推理（信息类专有）

抓到的东西立刻落盘，后续所有环节对快照做。理由：① 网页会变，不复现就不可审计
② 重试不必重抓（省配额）③ 溯源链的锚点只能是快照。

### 5.6 语义层只能引用，不能让每个 agent 各立一套

**约束包里的每个字段/指标，必须映射到 L-1 的共享语义。** 映射不上就必须**显式声明
`unmapped` + 理由**，不能默认放行。

**禁止的不是「系统产出语义层」，而是「每个 agent 各自形成理解」。**

个人版默认由 `OntologyPort` 从任务契约 + 输入数据 schema **自动起草**，起草完**立即冻结**、
写入 `ontology.yaml`、全局共用。起草是一次性的、显式的、可审的；
每个 agent 私下理解是多次的、隐含的、不可审的——**差别在这里，不在谁生成的。**

企业版可以把这条实现换成"导入既有标准"，`core/` 完全不知道区别。

### 5.7 不自己写 agent loop —— fork Hermes 的 loop

**agent loop（多轮工具调用）是已经解决好的问题**，重写只会引入新的 bug 来源。
但**直接当依赖也不行**——上游会漂。

**做法：fork `NousResearch/hermes-agent`（MIT）的 loop 核心，改造成 bobanana6 的 worker 运行时。**

三条理由：

```
① 那个 loop 里有大量【用真实事故换来的防御分支】——截断续接、上下文压缩、
   错误分类、角色交替修复、工具结果溢出落盘。自己写等于把这些坑重踩一遍。
② fork 后代码归我们，不受上游迭代节奏牵制。
③ MIT 允许 fork/修改/商用，要求保留版权声明和许可文本。
```

**fork 的边界（抄什么 / 扔什么 / 改什么）见 `FORK-NOTES.md`。**

接口不变：

```python
# core/ports.py
class AgentRuntimePort(Protocol):
    def run(self, subtask: Subtask, bundle: ConstraintBundle,
            ontology: Ontology, tools: ToolSet, budget: Budget) -> Candidate: ...
```

`agentloop/` 是它的实现（fork 来的），住在 core 之外。**core 不知道 Hermes 存在**（§9.1 有强制测试守着）。

**规模事实**：上游 `agent/` 是 312 文件 / 6.3 MB（≈15 万行），
但**主循环本体只 1835 行**——大头在上下文压缩（10,332 行）和故障恢复（5,561 行）。
**fork 后按 `FORK-NOTES.md` 砍到「几百行内核 + 几件套」。**

**"可以混用"仍然成立**：`AgentRuntimePort` 是端口不是类，将来要换 Claude Code / 自研 loop
也只是换实现。简单的块配轻 runtime，难的块配强的。

### 5.8 三层联通靠【工具】，不靠【提示词】

agent 怎么知道"复购率"在我们这儿指什么？怎么知道上游产出在哪？

**靠工具，不靠 prompt。这是本设计里最容易被做错的一处。**

直觉做法是"把语义层和契约塞进 system prompt"——但那只是**建议**。
多 agent 系统里建议会被长上下文稀释掉，**尤其在被切分出来的小块里，agent 只看到局部**。

**工具是【能力边界】，不是建议：**

```
语义层   semantics.lookup(term)     → 概念定义 + 单位 + 口径
         semantics.map(field)       → 字段 → 概念 id
         semantics.check(usage)     → 这个用法合不合语义

任务层   task.mysubtask()           → 我负责什么、输入在哪、输出到哪
         task.upstream(name)        → 上游产出的 schema 和实际路径
         task.contract()            → 接口契约

★判定    check.local()              → 立刻跑本块全部 hard，返回 Verdict
         check.provenance(...)      → 校验溯源链
         check.assemble_dryrun()    → 能不能拼上（不实际拼）

取数     sources.snapshot(ref)      → 拿固化的原始材料
```

**★ `check.local()` 是整个工具集里最重要的一个。**

它让 agent 在**提交前**就知道自己过不过——**直接把"约束出现得太晚"从系统层消掉了**
（这正是那 33 次跑测里最致命的一条：上限藏在拒绝消息里，模型烧到第 19 次调用才撞上）。

**但它的定位要写死**：`check.local()` 是**便利**，不是**信任基础**。
提交后系统会**独立再判一遍**，agent 的自检结果**不作数**（见 §5.9）。

**为什么工具 > 提示词（三条硬理由）：**

```
结构性  工具返回结构化结果，agent 不用猜；prompt 要靠理解
强制性  不调 task.upstream() 就不知道上游在哪，绕不过去；prompt 可以忽略
可审计  每次调用留痕，能回答"它当时查了什么"；prompt 注入无法追溯
```

### 5.9 agent 的自我报告不可信

**这条必须写死在设计里。** agent 说"我做完了"≠ 做完了。

```
不可信    agent 的自我报告（"已完成"、"已通过"）
不可信    agent 声称的自检结果
可信      系统独立跑的判定
```

**所以：提交是"交作业"，不是"宣布通过"。** 系统收到 Candidate 后独立跑 `admit()`；
agent 的 check 结果只用来减少往返，不参与判定。

**worker 级的三条保障：**

```
① 预算   每个 worker 有 token / 墙钟 / 调用数上限，超了强制终止并归类为【超预算失败】
② 权限   worker 只能读它声明的 inputs，只能写自己的 output 分区
         越界直接拒绝 —— 用【工具边界】实现，不是"请遵守"
③ 重述   每轮把 subtask.goal + 接口契约 + 相关语义重新注入
         防长任务里的目标漂移（agent 只看到局部，最容易丢的就是目标）
```

**失败必须可归因，不能停在现象层：**

```
超预算      预算参数不对，或子任务切得太粗
未通过      约束太严 / agent 能力不足 → 局部重试
工具误用    接口设计有问题 → 改工具签名，不是重试
崩溃        runtime 缺陷 → 换 runtime
```

**分类错了就修错了地方**：把"接口设计问题"当"能力不足"去重试，只会烧钱不出货。

### 5.10 从 Hermes 抄来的五条硬不变式

**这五条是 fork 的真正价值**——每条背后都有一个真实事故编号，都是"不知道就会踩"的坑。
完整 20 条见 `FORK-NOTES.md §3`。

**① 索引在列表被改写后一律不可信。**

压缩或修复会替换 dict、插入行，陈旧索引会让重放前缀**在本轮 tool 行中间裂开**，
孤立的 tool result 被静默丢掉。
→ **bobanana6 的装配器用内容指纹或稳定 id 定位，不要用位置。**

**② 「失败」也是一种必须被记录的状态。**

「候选失败了」和「候选从没跑过」必须是两个可区分的状态，否则重跑时会把旧的未回答输入重放一遍。
→ **装配器必须能区分这两者。**

**③ 单点收口。**

surrogate 清洗、tail 关闭、scaffolding 丢弃在 Hermes 里都刻意放在**唯一必经之处**。
→ **判定内核收敛成一个 choke point，而不是每条分支各写一遍。**

**④ 只有 provider 上报的真实用量才能重置熔断器，估算不行。**

rough 估算对非 ASCII 文本低估最多 ~2×，会把熔断器误重置成死循环。
→ bobanana6 用 token 预算估子任务规模时，**同一条纪律**。

**⑤ 临时验证不得 shadow 真套件。**

ad-hoc 验证只在该项目**完全没有** canonical 命令时才启用，且一律 scope=targeted，不得升格为 full。
另外两条同族：**exit code 归因规则**（管道/后台/`&&` 不得冒充）、**编辑后证据过期**
（"改完代码后旧测试不算数"是显式时间戳比较，不是靠 agent 记得）。

### 5.11 错误 → 三决策映射（本项目核心诉求的落地）

bobanana6 要求「失败能精确归因 → 决定局部重试 / 改切分 / 改约束」。
在 `ClassifiedError` 之上加一层枚举即可：

```
RETRY_LOCAL      rate_limit / overloaded / server_error / timeout
                 → 同 worker 退避重试

RESHARD_TASK     context_overflow / payload_too_large / 输出被截断 /
                 repetition / thinking_exhausted
                 → 【回传到切分层】：块太大或太难，拆更小

FIX_CONSTRAINT   format_error / role_alternation / 空响应 / 消息体非法
                 → 【请求形状错】：改约束或消息构造，重试和换源都没用

SWITCH_SOURCE    model_not_found / policy_blocked / upstream_blocked
                 → 换 worker / 模型 / provider

ABORT            解释器关闭 / billing / auth_permanent / content_policy_blocked
                 → 终止且不重试（后者是内容确定性的，同 prompt 必然再撞）
```

**两条判读纪律**（Hermes 用血换的）：

```
① 计分尺子分场景：413 用【字节】、token 溢出用 token/消息数。
   用错尺子会永远报「无进展」并卡死。
② 分类优先级是 load-bearing：413 必须排在通用 4xx 之前；
   context-length（含被包成 429 的输出上限错）必须排在非重试客户端错之前。
```

### 5.12 并发是默认前提，不是「外层的事」

**bobanana6 的卖点就是并发。** 但 §5.7 的 worker 规格最初假设自己**独占运行**——
这个假设不成立：**N 个 worker 打的是同一个端点。**

**推论：并发不是 cluster 层单独能解决的问题，`agentloop/` 必须参与。** 四件事：

```
① 主动限流 ≠ 被动重试
   被动：撞了 rate_limit 再退避（§5.11 已有）
   主动：【事前就不发出去】（令牌桶 / 并发闸）
   ★ N 越大，撞限流的概率越高 —— 并发放大的不是总量，是【撞墙频率】

② 击穿（这个 regime 下最要命）
   同一个子任务被多个 worker 同时重试 → 同时打模型
   → 单飞（single-flight）：同一个 key 的请求在途时，后来者【等待】而不是再发
   ★ 局部重试的并发度越高，重复打模型越严重 —— 这是 §4.2 那条决策的隐藏成本

③ 会话隔离
   多 worker 并发时状态不得串（`AgentIO.persist` 需要隔离语义）

④ 请求级模型路由
   简单块配便宜模型、难块配强模型 —— §5.7 承诺了「runtime 可以混用」，
   这里是那个承诺的落点
```

**★ 补强（来自 DeepSeek Harness 的源码级实践）：**

**① 工具并发要分【调用级】，不是工具级。**

```
不是问"这个工具能不能并行"
而是问"这一次调用能不能并行"

每一次待执行调用动态分类：
  parallel   —— 可与相邻安全调用重叠
  exclusive  —— 必须独占，形成顺序屏障

执行用【滚动并发池】，
★ 但结果必须仍按【模型调用的原始顺序】写回。
```

**为什么调用级重要**：同一个工具，**只读参数可以并行、写参数必须独占**。
工具级标记表达不了这个区别 —— 而它恰恰是最常见的情形。

**★ 附带一条社区口径（PingCAP）**，把顺序说清了：

```
Agents fail, retry, and explore in parallel.
→ 三个要求，按此顺序：
   ① isolated workspaces   （一次尝试不能污染另一次）
   ② concurrency controls
   ③ rollback
```

**② 沙箱要 fail closed，不悄悄降级。**

```
无法落实隔离策略时 → 【拒绝执行】，而不是静默降级为无限制执行。
```

**这条与 `secret_scope` 的 fail-closed 是同一条纪律**：
**安全边界降级必须是显式的、可见的**，不能是"没配好就放开"。

### 5.13 状态与恢复：重试便宜，才有资格把 N 开大

§4.2 说「**局部重试是 N 能开大的前提**」。这句话还有一个没写出来的前提：

**局部重试必须便宜。**

没有 checkpoint 时，一次失败重试的代价 = **整个子任务从头再来**。
N 越大，重试次数越多，成本按 N 线性放大 ——
**「局部重试」名存实亡，退化成「整块重跑」。**

**所以 checkpoint 不是「锦上添花的健壮性」，是 §4.2 那条决策的成本前提。**

两条从 Hermes 抄来的纪律（`FORK-NOTES.md §3`）：

```
① 【失败 turn 也必须落盘成合法状态】
   「候选失败了」和「候选从没跑过」必须可区分 ——
   否则续跑时会把旧的未回答输入重放一遍

② turn 边界是唯一落盘点（单点收口）
   不在每条分支各写一遍
```

**★ 补强（来自 DeepSeek Harness 的源码级实践）：**

**① 事件日志是【唯一真相源】，模型上下文是它的投影。**

原设计里 `events.py` 只是"给归因用"的旁路记录 —— **这个口径太弱**。
更强的做法：

```
会话 = 【只追加的事件日志】（turn/start、step/start、消息、chunk、
        工具调用与结果、结束边界 全部进日志）
模型看到的上下文 = 由日志【投影】出来（deriveMessages），
                   而不是另一份独立维护的状态

原则：★「模型可见即已记录」
```

**为什么必须这样**：很多 agent 系统同时维护三份相似但不一致的状态 ——
**发给模型的上下文 / 展示给用户的记录 / 用于恢复的快照**。
一旦三者漂移，就出现最难查的 bug：**界面上看到了某条消息，但模型没看到；
模型依据某段隐藏上下文做了决定，但重启后那段上下文丢了。**

**→ bobanana6 采纳此口径**：`events.py` 从"旁路日志"升格为**唯一真相源**。

**② Crash Recovery 的具体动作（把"失败也落盘"变成可执行）。**

```
载入时若发现一个 turn/start 没有配对的 turn/end：
  ★ 不粗暴截断已持久化的长任务，
    而是【补一个 interrupted 结束事件】，保留中断前已发生的事实。
```

**★ 这条直接补上了原方案只有原则、没有动作的缺口。**

### 5.14 责任归因：三决策的前提

**这是本次审查发现的最大概念缺口。**

§5.11 的 `BobananaAction` 分的是**错误类型**（rate_limit / timeout / context_overflow）
→ 决定**重试策略**。

**但 §4.1 的三决策（改切分 / 改约束 / 局部重试）要的不是「这个错属于哪一类」，
是「这次失败该怪谁」。这是两件事：**

| | 输入 | 输出 |
|---|---|---|
| 错误分类 | 异常对象 | 重试策略 |
| **责任归因** | 失败的任务 + **轨迹** | **改哪一层** |

**为什么分不出来会致命**：`context_overflow` 既可能来自「块太大」（→ 改切分），
也可能来自「历史没压缩」（→ 改约束）。
**只按错误类型分类，这个岔路口是瞎的 —— 而 §4.1 的三决策正好站在岔路口上。**

**归因的四个出口：**

```
模型不知道      → 知识缺失    → 换 worker / 补语义层
工具坏了        → 调用错误    → 换源 / 修工具
上下文没给到    → 检索·构造   → 改约束
判定器太严      → 约束缺陷    → 改约束（松绑）
```

**判据（可直接做成实验）：**

> 把该 worker 拿到的上下文**原封不动**交给一个正常人 —— 他能答对吗？
> - **能** → 模型的锅（prompt 约束 / 拒答策略）
> - **不能** → 上游的锅（检索 / 切块 / 工具 / 数据）
> - **答得出，但与 worker 答的不一样** → **模型忽略了上下文**（LITM）→ 改排布

**这条的价值**：把「模型幻觉了」这个不可证伪的说法，变成一个**当场能做的实验**。

**★ 层级纪律**：归因是**判定器的输入**，不是判定器本身。归因错了，重试/改切分全打偏。

### 5.15 可观测：事件流是归因的唯一数据源

§5.14 的归因需要**轨迹**。轨迹从哪来？**结构化事件流。**

```
每次工具调用 / 每次重试 / 每次截断 / 每次 gate 检查 = 一条事件
字段：task_id + worker_id + 序号 + 类型 + 耗时 + 结果摘要
```

**为什么不能靠读日志：**

1. 日志是**给人看的散文**，归因要的是**可程序化判定的字段**
2. §9 的纪律「归因必须到具体角色 / 具体缺陷，不能停在现象层」——
   **没有结构化事件，就只能停在现象层**

**指标口径**（直接决定「这版改动算不算变好」）：

```
工具：调用准确率 / 参数正确率 / 任务成功率 / 失败恢复率
交付：answer correctness / citation / faithfulness / 拒答准确率
★ 汇总数字必须拆开算 —— 表面数字里常混着「回退必对」白送的部分
```

### 5.16 自愈与兜底：烧完资源之后给什么

**「不认输 = 把资源全部烧完再交兜底」** —— 那么**兜底是什么**？现在的规格里没有落点。

**三级出口：**

```
① 反思（Reflexion）≠ 重试
     重试 = 同样的输入再打一次          → 治【瞬时故障】
     反思 = 把失败原因【加进上下文】再打 → 治【能力不足】
   ★ 现在只有前者

② 降级单 agent
     当切分本身是错的（块之间根本不可独立验证），
     继续重试 / 换源都是白烧钱 → 【退回单 agent 干这一块】
   ★ 这是「先单后拆」的逆向路径，也是 N→1 的合法出口

③ 拒答是第三种合法结果
     现在 gate.py 是二分（过 / 不过） → 逼 worker 在
     「交了但错」和「不交」之间选
     而「明确报告我拿不到这个信息」更便宜
   ★ 对应硬约束：a wrong answer is scored, an exception is not
```

**再加一件：taint 机制。**
同一个工具连续失败 N 次后，**主动提示换工具**，而不是继续通用重试。
**在弱模型上这是最大的省钱项** —— 弱模型最典型的死法就是在一个坑里反复跳。

### 5.17 两条被我删过头的（自我修正）

`FORK-NOTES.md` 的 C 类（直接删）里，我把「上下文压缩全套」划掉了。**删过头了。**

**① 可恢复降级不能删。**

课程判据：上下文超限三策略 = **截断 / 摘要压缩 / 可恢复降级**，
其中「可恢复（分层摘要 + 原文）」是**必答项，不是可选优化**。

**为什么在这个项目里是必答**：bobanana6 的成败取决于「块切得对不对」。
压缩如果**不可恢复**（摘要覆盖原文），一次长任务失败就**拿不到原始证据**——
**不可恢复的压缩会切断 §5.14 的归因链，把自己的诊断能力废掉。**

**附一条实测结论（省 token 不是选型依据）**：

```
超限三策略的 token 数几乎一样  ⇒ 省 token 不构成选型依据
真正的判据是【可恢复性】和【缓存友好性】
```

**② 前缀缓存友好的 prompt 组装纪律。**

**多 agent 拆分天然破坏前缀缓存** —— N 个 worker 的 prompt 前缀各不相同，
缓存全军覆没，**每个 worker 都要全量 prefill**。这是拆分的一项隐性成本。

而 **`agentloop/` 是唯一能控制它的地方**：组装时把
「稳定的共享语义 + 子任务公共前缀」放**前面**、「worker 特有的动态数据」放**尾部**。

**判据**：前缀改动越靠前，缓存失效越彻底 ——
系统提示词首行改动会让缓存几乎全废，而尾部改动只影响一点点。
**所以「什么该放前面」不是排版偏好，是成本决策。**

### 5.18 前置实验：worker 模型的能力门槛（**先于一切**）

**这条不是设计，是前置门禁。**

`arXiv:2607.27942` 在标准化 benchmark 上给出一条实证边界：

> scaling 带来可测的准确率提升、成本约线性增长 ——
> **但【仅当底层 LLM 超过最低能力门槛】才成立**

**这直接决定本项目的立论成不成立。** bobanana6 的 worker 计划用弱模型 / 免费小模型。
**如果目标模型过不了门槛，"用充裕并发砸任务"就变成只增加数量、不增加能力** ——
而论文说这种情况下 scaling 是无效的。

**实验设计（要能证伪）：**

```
固定一个子任务（与 §12.4 压力任务同族，但小得多）
让目标 worker 跑 N=10 次，不看【答得对不对】，只看三件事：

  ① 能不能稳定产出【可被判定】的产物（格式完整 / 可解析 / 可验证）
  ② 产物里有没有自陈的「我没拿到这个信息」（拒答能力）
  ③ 失败时能不能给出可归因的错误，而不是静默产出垃圾

判据（★ 跑之前定死，别跑完再找理由）：
  可判定产物率 ≥ 阈值
  拒答能力有没有 —— 没有 = 它在硬编，后面所有判定都会被污染
```

**★ 为什么必须排在所有设计改动之前**：
门槛不过，**后面每一条优化都是在给一个不成立的前提做优化** ——
**先证伪比先优化便宜。**

**★ 万一不过门槛**（三条路，此处不展开）：
① 换更强的 worker（成本结构变）
② 缩小子任务粒度（让每块更简单）
③ 接受「强模型 1 个 + 弱模型 N 个」的异构编队
（`arXiv:2606.20629` 说异构团队持续占据成本-准确率前沿）

### 5.19 ClusterPolicy 的取值域与复杂度上限

**① 拓扑取值域直接借 AdaptOrch（`arXiv:2602.16873`）的四个规范拓扑：**

```
parallel      并行独立块（本项目的默认形状）
sequential    顺序依赖，不能并行
hierarchical  分层（一个 planner 装不下才分）
hybrid        混合
```

**理由：有外部定义可引。** 比自造词好 —— 文档、代码、面试都能对上。
AdaptOrch 报的收益：拓扑感知编排比静态单拓扑 **+12–23%（同一个底层模型）**。

**② 补一条硬判据：复杂度上限。**

`2607.27942` 实测：**性能在中间复杂度达峰，之后因超时与评测限制而下降。**

现在的 `split.py` 只有"接口密度够不够"（**能不能切**），
**缺"切到多复杂就过头了"（该不该止步）**。

```
现有判据：iface_complete / merge_cheap / round_budget …
新增：    complexity_ceiling
   依据    "#块数 × 平均块内轮数 × 装配成本" 的复合量
   超限时  不是"拒绝切分"，而是【停止细分】（保留当前粒度）
```

**★ 这条与 §9 的 fake parallelism 警告方向一致但不同**：
那条说"别为 N 而切"（**动机**问题），这条说"**即使切得对，复杂度也有物理峰值**"。

## 6. 约束 kind

| kind | 适用 | 判定 |
|---|---|---|
| `schema` | 两类 | 列名/类型/可空性 |
| `presence` | 两类 | 文件存在、行数达标 |
| `range` | 两类 | 值域，报第一个越界位置 |
| `invariant` | 两类 | 行内表达式 |
| `relation` | 两类 | 跨列/跨文件 |
| `provenance` | 信息类 | 每个点能指回快照；缺失率超限=不合格 |
| `corroboration` | 信息类 | 关键字段 ≥N 独立来源；**不一致不判失败**，进冲突通道 |
| `freshness` | 信息类 | 按快照时间戳判 |
| `coverage` | 信息类 | 覆盖指定源；**缺源必须显式声明** |
| **`concept_ref`** | **两类** | **字段必须映射到本体概念，或显式声明 unmapped** |
| **`unit_consistency`** | **两类** | **跨子任务传递的量单位一致，或声明了换算** |
| **`definition_pin`** | **两类** | **同一指标名钉在同一版本 Definition 上** |
| **`code_valid`** | **两类** | **编码值必须在 code_system 内** |
| `custom` | 两类 | 指向 `checks/` 下具名函数 |

**`custom` 不执行模型生成的代码。** 约束包是**数据**（参数），不是可执行文件。

**判定顺序**：`presence` → `schema` → `concept_ref` → 值类 → 溯源类 → 单位/口径类。

**`concept_ref` 排在值类之前**是有意的：语义错了，值对不对都不重要。

## 7. 自洽性检查

切分方案 + 约束包发给集群前必须先过：

```
contradiction      两条 hard 互斥
tool_missing       hard 引用了不可用的能力
unreachable        hard 要求的规模 > 预算
orphan_target      hard 指向不在 deliverables 里的文件
stale_blind        blind 条目已被某条 hard 覆盖
unsatisfiable_tol  容差 < 数据精度
cycle              切分图有环（违反星形）
missing_iface      子任务之间接口没有对应约束
unverifiable       ★ 某子任务无任何可判定 hard（不能局部重试）
★ write_serial     同级 write 子任务未串行化也未分区隔离
★ merge_expensive  合并成本超过阈值（违背 §4.4 三问之②）
★ concept_unmapped 约束包引用了本体论里没有的概念，且未声明 unmapped
★ def_version_mix  同一指标名引用了多个版本的 Definition
```

**任一命中，禁止启动集群。**

**`unverifiable` 和 `concept_unmapped` 是最容易被漏、后果最重的两条**：
前者让局部重试无从谈起（§4.2 的表立刻变灾难），后者让语义一致性失去保障。

## 8. 目标模型

选 GLM-4.7 因为 MIT（可自部署）、200K 上下文 / 128K 输出、原生 tool calling。
**换模型只影响 `adapters/`，core 一行不动。**

| | GLM-4.7 | GLM-4.7-Flash |
|---|---|---|
| 架构 | MoE 358B 总 / 32B 激活 | MoE 30B 总 / 3B 激活 |
| 上下文 / 输出 | 202,752 / 128K | 200K / 128K |
| 许可 | MIT | MIT |
| 访问 | 自部署或付费 | 免费，**但 1 并发** |
| 显存 BF16/FP8/INT4 | 859 / 430 / ~155 GB | 远低 |

**关键事实**：

- **1 并发**意味着 Flash 版**不能当集群用**——整条路线依赖并发槽，这条直接封死。
- **92 层全注意力**在 128K 下 KV cache 达 **46 GB**。"给每个 worker 塞满长上下文"不可行
  → **worker 之间靠契约通信，不靠共享长上下文**（Kimi 也是这个做法：
  subagent 只回报结论，不回报中间过程）。
- 8×RTX 3090（192GB）在 INT4 下理论上装得下（约 155GB）。

**小模型档位**：`Qwen/Qwen3.5-4B`（硅基流动，免费）。4B 正是本设计假设的"弱模型"——
**单个能力不足才显出分工和判定的价值。**

## 9. 业界实证参照

**这四条是四家独立得出的共同结论，不是我的推断。**

| 系统 | 规模 | 关键做法 / 结论 |
|---|---|---|
| **Kimi K3 Agent Swarm** | **300 subagent / 4000+ tool calls** | orchestrator 限 **15 步**；subagent 上下文隔离、**只回报结论**；**subagent 冻结，只训练 orchestrator** |
| **Anthropic 研究系统** | 3–5 subagent | orchestrator-worker；研究类任务 +90.2%（**breadth-first，读密集**） |
| **Cognition** | 未公开 | 从"别建多 agent"改为"**map-reduce-and-manage**"；**subagent 主要只读** |
| **OpenHands** | 数个 | **读密集能 fan out，写密集不行**；git worktree 隔离 |
| **Hermes Agent**（fork 来源） | 单 agent | 312 文件 / 6.3 MB；**主循环只 1835 行，大头在压缩(10,332)与恢复(5,561)**；**agent 的自我报告不可信**（证据 = 命令 + exit code，不是文字叙述） |

**Moonshot 自己公布的两个失败模式**（训练前的 orchestrator 会犯）：

```
① Serial collapse  指挥官回避协调，全丢给一个 subagent 慢慢做 → 退化成单干
② Fake parallelism 为了刷并行度指标，盲目切出一堆无意义子任务
```

**② 是这套设计最需要警惕的**：如果 KPI 是"N 大"，orchestrator 就会为了 N 而切。
Moonshot 的解法是奖励函数加两维——**真实并行度** + **子任务完成率**（防凑人头）。

**成本参照**：多 agent ≈ **4×** 单 agent ≈ **15×** 普通对话。

**一句话**：swarms 是编排框架，agentscope 是运行时框架，
**bobanana6 是"语义 + 验证 + 装配"框架**。

## 10. 完成体的功能

```bash
$ bobanana6 run task.yaml
#   默认：语义层自动起草
#   企业：$ bobanana6 run task.yaml --ontology ontology/credit.yaml  （导入既有标准）

[L-1] 语义层 ... 自动起草 credit-risk v1 | 概念 14 | 口径 9 | 编码表 2   (1 次模型调用)
               自洽性检查 ✓（无循环定义/单位自洽/别名不冲突）
               已落盘 .bobanana6/ontology.yaml  ← 可手改，下次直接复用
[L0 ] 契约   ... 交付物 9 | 可用源 12
[R0 ] 侦察   ... 源可达 9/12 | 实体 340 | 字段填充率 0.71        (只取样, 40s)
[R1 ] 切分v1 ... 9 块（按源）, 星形✓ 每块可验证✓ 语义映射✓
[L2 ] 内核   ... 18 hard / 6 soft / 4 blind / 3 unmapped(已声明)
[R2 ] 首轮   ... 限流闸 6/8 （主动，未撞墙）| 单飞去重 1 次 | 会话隔离 ✓
               7 过 / 2 失败（源4 反爬, 源7 超时）
               → 归因: 源4 = 工具坏(反爬) · 源7 = 瞬时(超时)
                 判据: 上下文给正常人 → 答不出 → 上游的锅
               → 局部重试【从 checkpoint 续，非整块重跑】:
                 源4 走渲染降级链✓ / 源7 二次✓
[   ] 事件流   ... 214 条（call 189 / retry 12 / truncate 3 / gate 10）
               工具成功率 0.91 | 失败恢复率 2/2 | 拒答 1（合法出口）
[R3 ] 细分   ... 字段 X 填充率仅 0.38 → 按时间窗再切 4 块（第 2 轮，达上限）
[R4 ] 交叉   ... 关键字段 23 | 多源一致 17 | 真冲突 4 | 口径不一致 2
[L4 ] 分歧   ... 4 条真冲突 → 记录并保留双方证据
                2 条口径不一致 → 归一后重比，1 条转一致、1 条转真冲突
[L5 ] 装配   ... 全局不变量 4/4 | 溯源完整度 100% | 合并成本 0.3×切分成本
[交付] 9/9 块合格, 装配通过
[产出] data.csv + summary.json + SOURCES.md + CONFLICTS.md + ONTOLOGY-MAP.md
```

**具体能做的事**：

1. **切得对**：先侦察再切；星形、可验证、语义映射三类检查；不合格不启动
2. **语义不飘**：所有字段钉在外部本体论上，`customer_id` 不会两个 agent 两个意思
3. **砸得动**：N 块并行，失败只重试那一块
4. **拼得上**：装配检查全局不变量 + 合并成本
5. **说得清**：每个点指回快照；真冲突保留双方；口径不一致单独归类
6. **可回放**：内核确定性 + 快照固化
7. **省得下**：重试从 checkpoint 续（不整块重跑）· 单飞去重 · 主动限流不撞墙
8. **怪得对**：失败归因到具体角色，三决策站在有依据的岔路口上
9. **兜得住**：反思 → 降级单 agent → 拒答，资源烧完还有合法出口

## 11. 明确不做

- 不做投票 / 辩论 / 多数决
- 不做非结构化 swarm（agent 互相协商的自由网络）—— 业界共识是干扰项
- **不合并三类分歧**（盲区/真冲突/口径不一致）—— 合并了就无法分别处理
- **不让每个 agent 各自形成语义理解** —— 必须有唯一一份、前置冻结的共享语义
  （默认**自动起草**，不是禁止系统产出；禁止的是"各立一套"）
- **不做不侦察就切分**（R0 强制）、**不做无轮数上限的迭代切分**
- **不做同级写操作并行**（除非分区隔离）
- 不做环状切分
- **`core/` 不 import 模型 SDK / HTTP 客户端**，不含 `prompt`/`token`/`http`/`url`/`html`
- `custom` 约束不执行模型生成的代码
- 不做约束的自动学习：只由切分器和仲裁产出，两条路都留痕迹

**§5.12–5.17 带来的新边界：**

- **不把「错误分类」当「责任归因」用** —— 两者输入输出都不同
  （异常→重试策略 vs 失败+轨迹→改哪一层），**不能互相替代**
- **不做不可恢复的压缩** —— 摘要必须能回溯到原文，否则切断自己的归因链
- **不让 worker 自己宣布完成** —— gate 独立跑，自检不作数（§5.9）
- **不做没有事件流的归因** —— 读日志猜不算归因
- **不假设 worker 独占运行** —— 并发是默认前提，限流/去重/隔离不是可选项
- **不把拒答当失败** —— 它是第三种合法结果，不是需要重试的异常

## 12. 验收标准（怎么证明它真的能用）

### 12.1 一句话

**验收不测「能不能做出来」，测「做得出来、且知道自己做到哪了」。**

理由：整套架构的设计重心（判定内核 / gate / 归因 / 三级出口）**几乎全在「发现不合格」上**。
只测「做出来」的验收，**测不到 90% 的设计**。

### 12.2 难度从哪来：攻击面覆盖率

**不是把任务做大。** 把任务做大只测出「上下文够不够」——
那是**容量测试**，不是架构验收。

**真正的难度 = 每一条架构断言都有对应的攻击面被触到。**

```
架构断言                          验收任务里必须存在的攻击面
────────────────────────────────────────────────────────────────
切分器能切出星形、可独立验证   →  天然网状依赖的源群（切分本身就是难题）
语义层能防住「各立一套」       →  同一概念在各源里本来就多义（同名不同口径）
判定内核区分「错」与「冲突」   →  两个权威源给出不同的值，且【都不是错的】
「缺失 ≠ 0」不被静默填平       →  源里故意留空缺格（且不标注）
局部重试能救回来               →  瞬时故障源（超时 / 限流）
救不回来时走对出口             →  持久故障源（已下线 / 需登录）
归因能定位到层                 →  同样的表面症状来自【不同的层】
装配检查能发现拼不上           →  块各自合格，但合并后违反全局不变量
拒答是合法出口                 →  有一块【真的不可能完成】
对不可分解任务要拒绝切分       →  一个【不该拆】的任务（负例）
```

**最后一条最容易被漏**：只测「该拆的拆了没」，不测「不该拆的拒了没」——
**后者才是 `fake parallelism` 的入口**（§9 里 Moonshot 公布的两个失败模式之一）。

### 12.3 五套集

| 集 | 规模 | 判据 | 什么时候跑 |
|---|---|---|---|
| **冒烟** | 3 个小任务，分钟级 | 块级通过率**不低于基线容差** | 每次改动前（门禁） |
| **主验** | 同形状 × 3 域 × 各 3 次 | 三口径（§12.5） | 阶段性 |
| **压力** | 1 个全攻击面任务 | §12.4 | 里程碑 |
| **反例** | 1 个「不该拆」的任务 | **必须拒绝切分** | 里程碑 |
| **注入** | 压力集 + 已知缺陷 | 发现 + 归因 + 出口 三者全对 | 里程碑 |

**⚠️ 冒烟判据不要用 reward 二值** —— 会把「能力波动」误诊成「架构回归」，
要用**通过数对比容差**。

**⚠️ 主验必须同窗对照旧版** —— 跨窗差异混了环境漂移，不可归因。

### 12.4 压力任务（尽量难）：跨源跨期跨语言的实体面板重建

**形状**：给定 **20–40 个异构源**，重建一张统一口径的「实体 × 时间」面板 + 一份冲突清单。

**「异构」的具体含义**（每一条都是攻击面）：

```
格式异构   HTML 表格 / 扫描件 PDF / API JSON / CSV / 纯文本年报
语言异构   中文 / 英文 / 日文 —— 实体名与字段名都不同写法
时间异构   财年 vs 日历年 · 公告日 vs 报告期 · 修订前 vs 修订后
单位异构   元 / 千元 / 百万元 混用，且【有的源不标单位】
结构异构   长表 vs 宽表 · 一实体一行 vs 一实体多行 · 缺失用 空/0/-/N/A
```

**交付物**：统一面板 + `CONFLICTS.md`（真冲突，双方证据都留）+ `SOURCES.md` + `ONTOLOGY-MAP.md`

**为什么这个形状最难**：它同时是 **信息类 + 半结构化 + 强全局约束**，
而这三者的交集正是「**单 agent 装不下、但切完又必须拼得上**」的那块地。

**它逐一命中 §12.2 的攻击面**：

```
网状依赖   实体 A 的 ID 要从源 7 拿到，才能去源 12 查它的另一段 → 天然挑战星形切分
多义概念   「营收」在四个源里四种口径（含税/不含税/合并/母公司）
真冲突     两个权威源对同一年给出不同的值 ——【都不是错的】
缺失陷阱   某些格子故意空着，且源里不标注
瞬时故障   两个源会超时 / 限流（可复现，用可控的假故障）
持久故障   一个源整体下线 —— 重试一万次也没用
同症异层   多个块报「算不出来」，但根因分别在：
           工具坏 / 上下文没给到 / 判定器太严 / 模型真不会
全局不变量 面板的每一列必须【跨实体口径一致】—— 单块内看不出来
不可能块   某实体的关键字段只存在于那个已下线的源里 → 必须拒答，不许编
```

**关键工程约束：ground truth 必须可构造，且构造过程不能泄漏给系统。**

```
主体：合成数据集（脚本生成，ground truth 由生成器持有）
      → 可控（能精确注入每种攻击）、可判定、难度可调
野生：混入少量【真实公开源】
      → 没有 ground truth，只测「能不能发现并声明它的不确定」
      ★ 合成数据太干净，模型会从规律里猜出答案 —— 野生部分是解药
```

**评测时 ground truth 与输入必须在物理上隔离**（不同目录 / 不同容器），
否则「模型没答对」和「模型偷看了」分不开。

### 12.5 判据口径：三个正交维度 + 两条纪律

```
块级   通过率          ← 每块合格
全局   装配通过        ← 整体拼得上
诊断   归因准确率      ← 发现 + 定位的能力      ★ 最容易被漏，最能区分好坏
```

**纪律一：不用单一总分。** 三个维度会朝不同方向动 ——
块级通过率涨了但装配挂了，是**过度切分**的信号；**总分掩盖这个**。

**纪律二：汇总数字必须拆开算。**
表面数字常混着「回退必对」白送的部分（§9 那条：表面 44.1%，拆开真实 10.5%）。
**不拆开会把污染程度看轻。**

**★ 每条结论必须附「本次没测到什么」**：
例如「拒答路径未被触发」「降级单 agent 未触发」。
**没被走到的出口 = 未验证的代码；沉默的能力等于不存在。**

### 12.6 反例清单：别拿这些当验收任务

```
✗ 需要人当裁判的（文风 / 审美 / 好不好用）    → 不可判定 = 不可验收
✗ 没有 ground truth 的                        →「看起来对」是最贵的错觉
✗ 本来就不可分解的（三方频繁共享中间状态）    → 测的是切分器的运气，不是架构
✗ 单次跑一个难任务                            → 抽签，不是验收
✗ 只有总分没有拆分的                          → 汇总掩盖污染
✗ 冒烟用 reward 二值当判据                    → 把能力波动误诊成架构回归
✗ 任务比资源小得多                            → 单 agent 就做完了，测不出分工价值
```

### 12.7 反例任务（测「拒绝」的能力）

**必须有一个任务是系统【应当拒绝切分】的。**

构造：三方需要**频繁共享中间状态**（§4.4 的「绝对不该拆」第①条）——
例如「在同一份状态机上做增量式互相依赖的推理」。

**判据**：系统必须**拒绝切分并降级单 agent**。
如果它切了，**这次验收失败** —— **哪怕结果做对了**。

理由：**切了也能做对**说明这次运气好，而 `fake parallelism` 的代价会在别的任务上还回来。
**验收要判的是机制，不是这一次的结果。**

### 12.8 三条最容易漏的

```
① 没有「失败样本」的验收等于没验收
   → 必须刻意构造「必然部分失败」的场景

② 没有「负例」的验收只测了一半
   → 该拆的拆了 ✓ · 不该拆的拒了 ✗ → 一半没测

③ 没有「未覆盖声明」的验收会高估自己
   → 每条结论都附「本次哪些出口没被走到」
```
