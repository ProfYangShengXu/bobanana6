## 1. 结构性问题（8 条）

### ① ★★★ `§5` 膨胀成 19 个小节，性质混杂

原文 `§5 设计决定` 是 **§5.1–§5.6 六条真正的设计判断**（切分离线 / 内核零模型 /
分歧三类 / 多样性来源 / 快照先行 / 语义唯一）。

后面陆续加的 **§5.7–§5.19 共 13 节，性质完全不同** —— 它们是**运行时层规格**：

```
§5.7–5.11   agent loop / 工具联通 / 自我报告 / 硬不变式 / 错误映射   ← 运行时接口层
§5.12–5.16  并发 / 状态 / 归因 / 可观测 / 兜底                      ← 运行时机制层
§5.17–5.19  自我修正 / 前置实验 / ClusterPolicy                     ← 门禁与收敛
```

**19 节平铺在「设计决定」下，读者找不到东西。** 这是追加式写作的必然结果。

### ② ★★★ 前置实验标着「先于一切」，却排在第 842 行

`§5.18` 的内文写着「**这条不是设计，是前置门禁**」「**为什么必须排在所有设计改动之前**」，
但它在文档里的位置是 **§5 的倒数第二节**。

**一个 blocking 的道具藏在附录位置** —— 读到 §5.3 的人不会知道后面有条门禁在等着。

### ③ ★★ `§5.17` 是写作过程的痕迹，不是设计内容

「两条被我删过头的（**自我修正**）」—— 这是**我改文档的历史**，不是架构的性质。
它的两条内容各有归属：

```
可恢复降级不能删   → 应并入压缩相关的正文
前缀缓存友好组装   → 已并入 §5.12（重复）
```

**读者不需要知道作者改过什么。**

### ④ ★★ `§5.13` 与 `§5.15` 讲同一件事的两面，且无交叉引用

```
§5.13 状态与恢复  →  「事件日志是【唯一真相源】，模型上下文是它的投影」
§5.15 可观测      →  「事件流是归因的【唯一数据源】」
```

**同一个事件流，两节各讲一半，读者会以为重复**（或以为矛盾）。
应合并成一节，或明确分工：**§5.13 讲落盘与恢复，§5.15 讲指标口径，事件流的定义只讲一次**。

### ⑤ ★ `§5.12`/`§5.13` 里堆着「★ 补强（来自 DeepSeek Harness…）」块

**追加式写作的痕迹**。这些内容的地位和正文一样（有些比正文更重要），
不该以"补丁块"的形式挂在节尾。**应融进正文。**

### ⑥ ★ `§5.4 多样性来源` 的定位需要重新审视

「切分维度 > 分解策略 > 温度」—— 这条写在早期（当时还没有 §5.19 的四拓扑）。
**它与 ClusterPolicy 的关系没有交代**：是同一层的两种说法，还是两层？

### ⑦ ★ 交叉引用断裂：`§9.1`

架构设计正文引用了 `§9.1`，但那门强制测试在**实现规格的 §9.1**。
要么补跨文档引用格式，要么在本文件里加对应小节。

### ⑧ ★ §5 的编号已经无法容纳新增

再加内容就没有地方放了（§5.20、§5.21…）。**结构本身需要升级。**

## 2. 内容性问题（3 条）

### ⑨ ★★★ `§5.7` 的结论已经过时，但正文没改

标题仍是「**不自己写 agent loop —— fork Hermes 的 loop**」。

但文献情报 §6 的结论是：

```
Hermes 的 loop 是【单 agent 的】—— 解决"上下文会爆"和"各种错怎么恢复"，
  对【多 agent 运行时】几乎没有设计。

DeepSeek Harness 解决的正是【多 agent 运行时】。
  bobanana6 的 14 条缺口里，至少 8 条它有现成答案，而且更细。
```

**结论动摇了，正文没同步。** 现在我方文档里同一件事有两个说法。

### ⑩ ★★ 验收只覆盖了一类任务

`§2` 明确写「**两类任务，两套切法**」（信息类 + 代码类），
但 `§12` 的压力任务**只设计成信息类**（跨源跨期跨语言的实体面板重建）。

**代码类任务没有任何验收任务** —— 而"多 agent 写代码"恰恰是 §4.3 说可切分性最好的场景。
**最该验的那一类没验。**

### ⑪ ★ 指标口径散落在两处

`§5.15` 有指标口径，`§12.5` 也有判据口径。**两处没有互相引用**，
读者不知道哪个是"开发时看的"、哪个是"验收时看的"。

## 3. ★★★ 最深层的问题：功能面在膨胀，但缺「核心 vs 可选」视图

**前面 11 条都是文档结构问题。这一条是架构问题。**

数一下现在累出来的东西：

```
3   层约束（L-1 / L0 / L1）
8   层目录（core / agentloop / ontology / decompose / contract / services / adapters / sources）
14  agentloop 文件
40+ 条设计决定
14  个约束 kind
15  条自洽性检查
6+1 条切分合法性（含新增 complexity_ceiling）
5   套验收集
12  个验收攻击注入点
```

**问题不是"太多了"，是「没有一条线说明哪些不做就不是 bobanana6」。**

这份文档现在的读者（包括未来的 dsh）面对的是：**40 多条并列的设计决定，没有优先级。**
后果很实际：**改动时不知道该先保哪个、可以让哪个**。

**这也带来一个真实的风险**：项目定位是**面向个人开发者**（§1.2 明确写了）。
但一个 8 层目录、14 个运行时文件、40+ 条设计决定的系统 ——
**个人开发者拿不拿得起来？**

**（注意：这不是提议分期交付。用户已明确反对 V0/V1/V2 分期。
这里要的是【优先级视图】——哪些是承重的、哪些是锦上添花。
范围边界（明确不做）本来就要保留。）**

## 5. 我建议的收敛顺序

```
第一步（不改架构，只改结构）    A + B + D
   → 拆章、前置实验提位、删痕迹
   零设计风险，立刻改善可读性

第二步（同步结论）              E + H + I + J
   → 把 §5.7 改到与文献一致，修断链，融补丁块

第三步（补缺）                  F
   → 补代码类验收任务

第四步（做减法）                G + K
   → 优先级表 + 交代 §5.4 与 §5.19 的关系
   ★ 这一步会【暴露】哪些其实可以砍掉 —— 到那时再决定
```

**⚠️ 一条纪律**：收敛不是重写。**每一步都应该是可验证的机械操作**
（拆章 = 改标题层级；合并 = 删重复段；改结论 = 替换一段），
**不要借收敛之名重写全文** —— 那会引入新的不一致。
